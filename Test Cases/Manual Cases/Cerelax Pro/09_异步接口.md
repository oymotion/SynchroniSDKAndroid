# Cerelax 异步接口用例（ASYNC-*）

> 覆盖 async 变体接口，补齐同步用例的覆盖缺口。
> 说明：所有 async 方法需在 asyncio 事件循环中 `await` 调用（可用 `asyncio.run(...)` 包裹）。
> 签名与同步版本一致，仅返回可等待对象；`asyncMulti*` 需 ≥2 台，缺设备则"跳过"。

### ASYNC-FUNC-010 async/sync 混用行为明确（各平台实测口径不同）
- **优先级**：P0
- **测试目的**：验证 async/sync 混用边界，避免误用导致状态错乱或挂起。
- **流程与逻辑**：
  - Python：在 `asyncio.run()` 协程内调同步 `connect()/init()/disconnect()`，记录返回值、阻塞时长与 `deviceState`；另在 SDK 回调线程内调同步接口，观察异常。
  - Android（Kotlin，AAR 1.4.6）：先跑纯 async 链路（`connectAsync` + suspend `init/start/stop/disconnect`）；再连接后断开，在 SDK 回调线程（`SensorCapiCallbacks`，状态回调）内调 `getBatteryLevelSync()`，观察是否被拒绝。
- **预期结果**：
  - Python 1.4.4 实测：「事件循环内调同步接口返回 None」不成立。同步接口会把协程投递到 `sensor-sync-loop` 后由当前线程阻塞等待，因此在用户协程内调用不抛异常、不返回 None，而是阻塞事件循环至完成（connect 最长约 110s），返回 True/False；`deviceState` 不会停在 Disconnected。真正的拒绝发生在 SDK 回调线程内：抛 `RuntimeError: blocking sync call from an SDK callback thread`。
  - Android 预期：在 SDK 回调线程内调 `getBatteryLevelSync()` 应抛 `IllegalStateException`（不阻塞、流不挂起）；纯 async 链路状态迁移正确。若返回缓存电量而非异常，说明未命中线程守卫，需要换注入点，不能判 PASS。
  - 用例如实记录各平台差异，不判为「无冲突」。
- **有效性说明**：明确「混用」在各平台的真实行为与拒绝条件，防止把「卡住」误判为「被拒绝」；纯 async 与纯 sync 路径需各自验证正确。
- **可自动化**：auto
- **人工介入**：无
- **测试结果**：待测试

### ASYNC-FUNC-011 asyncMultiStartDataNotification 同步起流（需 ≥2 台）
- **优先级**：P1
- **测试目的**：验证异步多设备同步起流。
- **流程与逻辑**：两台 init 后调用 multiStart，逐台检查结果并确认真实收到数据。参数按型号分层：同型号 `timeout=30s / maxDelayDispersionMs=5 / maxAttempts=3`；混型号 `60s / -1 / 5`（关闭首包离散度判定，避免异构对端时序导致误报）。
- **预期结果**：逐台均 `ok=true` 且真实收到数据。Python 返回 `[{mac, ok, error}]`；Android 返回 `Pair<Map<mac,Boolean>, Map<mac,String>>`。
- **有效性说明**：异步同步起流正确；混型号若仍报 dispersion，应归因于异构对端首包时序，不是 Cerelax 能力问题。
- **可自动化**：auto
- **人工介入**：无（缺 ≥2 台则跳过）
- **测试结果**：待测试

### ASYNC-FUNC-014 SensorAlgo init 重复调用幂等
- **优先级**：P1
- **测试目的**：验证重复初始化的行为。
- **流程与逻辑**：连续两次 `init()`。Android 侧附加间接证据：init×20 与 init×1 对同一批样本输出一致；init/destroy×200 采样 VmRSS 与 fd 数趋势。
- **预期结果**：第二次仍返回 True 且 `hasInit()` 保持 true，不崩溃、不重复分配资源。
- **有效性说明**：避免调用方重复初始化导致泄漏。「不重复分配资源」无法直接观测，只能用输出一致性与内存/fd 趋势做间接验证，最终契约需 native 确认。
- **可自动化**：auto
- **人工介入**：无
- **测试结果**：已实现（Demo 自动化；2026-11 真机：init×20 输出一致，init/destroy×200 RSS 335.7→336.3 MB、fd 222→224，无线性增长）

### ASYNC-FUNC-015 SensorAlgo destroy 后可重新 init
- **优先级**：P1
- **测试目的**：验证资源释放与复用。
- **流程与逻辑**：`destroy()` 后读 `hasInit()`；对旧实例再 `init()` 观察返回；随后新建 `SensorAlgo` 实例并 `init()`。
- **预期结果**：`destroy()` 后 `hasInit()==false`；Android AAR 的 `destroy()` 会把 `nativeHandle` 置 0，旧实例不可复用（再 `init()` 返回 False），复用需新建实例——新实例 `init()` 返回 True、`hasInit()==true`。
- **有效性说明**：避免算法实例泄漏；Android 侧「复用」语义为新建实例，而非对已销毁实例重复 init。
- **可自动化**：auto
- **人工介入**：无
- **测试结果**：已实现（Demo 自动化，待真机验证）
