# OB6000C 连接与状态机用例（DEV-SM-*）

> 下列用例均针对 OB6000C 单台执行（DEV-SM-011 需 ≥2 台）。
> 状态常量：`DeviceState.DISCONNECTED / CONNECTING / CONNECTED / READY / DISCONNECTING / INVALID`（Java `int` 常量）。
> 状态回调：`setOnStateChangeListener { profile, state -> }`；错误回调：`setOnErrorListener { profile, msg -> }`。
> 连接/断开优先使用 suspend 扩展 `connect()` / `disconnect()`（返回 `Boolean`），或 `connectAsync()` / `disconnectAsync()`（`CompletableFuture<Boolean>`）。

### DEV-SM-001 connect 成功，状态迁移 Disconnected→Connecting→Connected→Ready
- **优先级**：P0
- **测试目的**：验证连接成功与状态迁移序列。
- **流程与逻辑**：`setOnStateChangeListener` 注册回调并记录 `DeviceState.nameOf(state)`；`requireSensor(mac)` 后调 `connect()`（suspend），等待 `DeviceState.READY`。
- **预期结果**：`connect()` 返回 `true`；状态按 `DISCONNECTED→CONNECTING→CONNECTED→READY` 迁移（允许省略中间态但不得倒退）；最终 `getDeviceState()==DeviceState.READY`、`isReady()==true`。
- **有效性说明**：连接是后续操作前提；迁移顺序错误会导致指令在错误状态下发送。
- **可自动化**：auto
- **人工介入**：无
- **测试结果**：待测试

### DEV-SM-015 disconnect 后重新 scan 可再次发现设备
- **优先级**：P1
- **测试目的**：验证主动断开后，同一台设备可被再次扫描发现。
- **流程与逻辑**：`scan()` 匹配目标并记录 MAC → `requireSensor` → `connect` 到 READY → `disconnect` 到 DISCONNECTED → 重新 `scan()`（带重试，MAC 精确匹配同一台设备）。
- **预期结果**：断开后重新扫描结果包含同一 MAC `78:1C:9D:E4:6C:6B`。
- **有效性说明**：若断开后扫描找不到该设备（被 SDK 当作「已连接/已知」而过滤），会影响重连与多设备管理，属缺陷。
- **可自动化**：auto
- **人工介入**：无（设备上电在范围内为运行前置）
- **测试结果**：待测试

### DEV-SM-017 onAutoReconnect 回调反映重连状态变化
- **优先级**：P1
- **测试目的**：验证自动重连状态变化可观测。
- **流程与逻辑**：Android AAR **无独立的 `onAutoReconnectingStateChange` 回调**，等价观测方式为：注册 `setOnAutoReconnectListener { profile, restore, answer -> }`，连接起流后断电触发自动重连，记录进入重连与恢复后的回调，并同步轮询 `isAutoReconnecting()`。
- **预期结果**：进入重连阶段 `isAutoReconnecting()==true` 且 `setOnAutoReconnectListener` 被触发；恢复后 `isAutoReconnecting()==false`；`profile` 为对应 `SensorProfile` 实例。
- **有效性说明**：Android 回调模型与 Python 不同，本用例按等价映射执行（非 SKIP）；若后续 AAR 新增独立回调，则改为直接断言该回调。
- **可自动化**：semi-auto
- **人工介入**：人工断电/移出范围后恢复。
- **测试结果**：待测试
