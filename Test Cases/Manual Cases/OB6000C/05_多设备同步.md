# OB6000C 多设备同步用例（MULTI-*）

> 本组需 **≥2 台设备**。可用 2 台 OB6000C，或 OB6000C 与其它已登记型号混合。若只有 1 台，整体「跳过（缺设备）」，不判失败。
> Android 签名（Kotlin suspend 扩展）：
> - `multiStartDataNotification(sensors: List<SensorProfile>, timeoutMs: Int, maxDelayDispersionMs: Int, maxAttempts: Int)`，返回 `Pair<Map<mac, Boolean>, Map<mac, String>>`（结果 + 错误信息）；
> - `multiStopDataNotification(sensors: List<SensorProfile>, timeoutMs: Int)`，返回同上结构。
> 也可以走回调式 `multiStartDataNotification(sensors, timeoutMs, maxDelayDispersionMs, maxAttempts, OnMultiResultListener)`。
> 与 Python 的差异：`timeout` 由秒改为**毫秒**；结果以 MAC 为键的 Map 返回，不再返回 dict 列表。

### MULTI-FUNC-001 两台同时起流
- **优先级**：P1
- **测试目的**：验证多设备同步起流。
- **流程与逻辑**：两台均 `connect` + `init` 到 READY，调 `multiStartDataNotification(listOf(s1,s2), 30000, 5, 3)`，检查返回的 `Map<mac,Boolean>` 与两台 `isDataTransfering()`/数据回调。
- **预期结果**：两台对应 MAC 的返回值均为 `true`；两台均收到数据（EEG 流按 `getDeviceMac()` 归属正确）。
- **有效性说明**：同步起流核心能力。
- **可自动化**：auto
- **人工介入**：无
- **测试结果**：待测试

- **预期结果**：两台对应 MAC 的返回值均为 `true`；两台均停流，回调停止。
- **有效性说明**：同步停流。
- **可自动化**：auto
- **人工介入**：无
- **测试结果**：待测试

### MULTI-FUNC-003 某台未 Ready 不影响其余起流
- **优先级**：P1
- **测试目的**：验证部分失败不影响整体。
- **流程与逻辑**：一台 READY 且已 `init`，另一台仅连接未 `init`（或未连接），调 `multiStart`。
- **预期结果**：READY 台起流成功（Map 中为 `true`）；未 Ready 台为 `false` 且错误 Map 有原因；其余不受影响，不崩溃。
- **有效性说明**：容错。
- **可自动化**：auto
- **人工介入**：无
- **测试结果**：待测试

### MULTI-FUNC-004 首包时差 ≤ maxDelayDispersionMs
- **优先级**：P1
- **测试目的**：验证同步对齐质量。
- **流程与逻辑**：用默认参数（`timeoutMs=30000`、`maxDelayDispersionMs=5`、`maxAttempts=3`）`multiStart`；统计两台首个 EEG 批的 `getStartTimeStamp()`/`getDelay()` 差；超差应自动停流重试至 `maxAttempts`。
- **预期结果**：时差 ≤ 5ms；若重试后仍超差，明确判 FAIL 并记录两台时间戳。
- **有效性说明**：同步精度指标；`startTimeStamp` 为毫秒级锚点，比较前统一单位。
- **可自动化**：auto
- **人工介入**：无
- **测试结果**：待测试

### MULTI-FUNC-008 两后端各测对齐下发
- **优先级**：P1

- **流程与逻辑**：**Android 不适用**：SDK 固定使用系统原生 BLE，无 dongle/后端切换，`multiStartDataNotification` 只有一条 BLE 实现路径。
- **预期结果**：不适用，记 SKIP。

### MULTI-FUNC-009 跨设备 startTimeStamp 散布与 getDelay 符合预期
- **优先级**：P1
- **测试目的**：验证时延指标。
- **流程与逻辑**：`multiStart` 后统计各设备首个 EEG 批的 `getStartTimeStamp()` 散布与 `getDelay()`，并与 `multiStart` 的 `maxDelayDispersionMs` 对照。
- **预期结果**：散布在 `maxDelayDispersionMs` 范围内（默认 5ms）；`getDelay()` 为非负合理值（不因回放/实时路径不同而异常放大）。
- **有效性说明**：同步与延迟量化；`getDelay` = 首个原始数据包 bin 时间戳 − `startTimeStamp`，是起流时序锚点，不是信号数据。
- **可自动化**：auto
- **人工介入**：无
- **测试结果**：待测试

### MULTI-BND-001 multiStart/multiStop 空集合 / 单台 / 非法参数不崩溃
- **优先级**：P1
- **测试目的**：验证多设备起停接口对空集合、单台设备、非法参数都能安全处理。
- **流程与逻辑**：`multiStart(emptyList())`、`multiStart(单台)`、`multiStart(含 null/非法对象)`；`multiStop` 同理。
- **预期结果**：空集合返回 `false`/空结果且不崩溃；单台正常起流；非法参数被拒绝。
- **有效性说明**：多设备接口必须容错，不能因空集合或单台场景崩溃。
- **可自动化**：auto
- **人工介入**：无
- **测试结果**：已实现（Demo 自动化，待真机验证）

### MULTI-BND-003 multiReplayBinFile paths/sensors 长度不匹配或空串被拒绝
- **优先级**：P1
- **测试目的**：验证多 bin 回放接口对参数不一致、空路径、空 sensors 的容错。
- **流程与逻辑**：构造 `paths` 与 `sensors` 长度不一致、含空串路径、`sensors=null` 三组参数调用 `multiReplayBinFile`。
- **预期结果**：返回错误或被拒绝；不崩溃；不产生半启动回放。
- **有效性说明**：多 bin 回放参数由上层拼装，长度不匹配是常见错误。
- **可自动化**：auto
- **人工介入**：无
- **测试结果**：已实现（Demo 自动化，待真机验证）
