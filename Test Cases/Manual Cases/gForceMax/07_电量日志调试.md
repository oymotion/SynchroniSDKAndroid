# gForceMax 电量/日志/调试用例（BATT-* / LOG-*）

> **Android 口径**：`SensorProfile.getBatteryLevel(): Int` 为 suspend 扩展；电量回调为
> `setOnPowerListener { profile, level -> }`；电量刷新周期由 `init(packageSampleCount, initTimeoutMs,
> powerRefreshIntervalMs)` 的第三参决定。日志侧 Android 用
> `controller.setParam("LOG_PATH", dir)` + `controller.setParam("DEBUG_ENABLED", "True"/"False")`
> 控制 controller 级日志，`controller.log(msg, level)` / `profile.log(msg, level)`（level ∈ D/I/W/E）
> 写应用日志；profile 级 `setParam("DEBUG_LOG_PATH", "True")` 亦可开启设备日志。

## 电量（BATT-*）

### BATT-FUNC-001 getBatteryLevel 返回 0~100（或 -1）
- **优先级**：P1
- **测试目的**：验证电量读取。
- **流程与逻辑**：Ready + init 后调 `getBatteryLevel()`。
- **预期结果**：返回 `0..100`；无有效读数返回 `-1`（记录，不判失败）。
- **有效性说明**：电量接口可用；`getBatteryLevel()` 为 suspend，需在协程中调用。
- **可自动化**：auto
- **人工介入**：无。
- **测试结果**：待测试

### BATT-FUNC-002 setOnPowerListener 上报 0~100，±2% 滞回，不报 -1
- **优先级**：P1
- **测试目的**：验证电量回调。
- **流程与逻辑**：init 后注册 `setOnPowerListener`，观察上报值（可改变功耗/等待电量变化），记录每次 level。
- **预期结果**：上报 `0..100`；不报 `-1`；1% 抖动被过滤（相邻上报差值 ≥2 或相等）。
- **有效性说明**：回调稳定性；短窗口内电量不变属正常，判据为"无非法值 + 无 -1"，不强制要求出现变化。
- **可自动化**：semi-auto
- **人工介入**：人工制造电量变化或长时间观察。
- **测试结果**：待测试

### BATT-FUNC-003 powerRefreshInterval 决定上报周期
- **优先级**：P1
- **测试目的**：验证刷新周期。
- **流程与逻辑**：分别以 `powerRefreshIntervalMs=1000` 与 `2000` 执行 `init(20, 30000, interval)`，注册 `setOnPowerListener`，统计 30s 内回调次数与相邻间隔。
- **预期结果**：回调周期与设置一致（允许 ±20% 抖动）；1000ms 组次数约为 2000ms 组的两倍。
- **有效性说明**：周期参数生效；需重新 init 使周期生效（改周期不通过 setParam）。
- **可自动化**：auto
- **人工介入**：无。
- **测试结果**：待测试

### BATT-FUNC-004 startDataNotification 起流期间 setOnPowerListener 持续回调
- **优先级**：P1
- **测试目的**：验证起流后电量回调不会停止（针对"起流一段时间后 onPowerChanged 停止调用"的失效模式）。
- **流程与逻辑**：
  1. 连接 → Ready → `init(20, 30000, 1000)`（刷新周期取 1000ms，便于短时间观察多次回调）。
  2. 注册 `setOnPowerListener`，记录每次回调到达的时间戳（不关注电量值是否变化）。
  3. `startDataNotification()` 起流（`NTF_EMG` + `NTF_IMU`）。
  4. 起流后持续观察 ≥10 分钟，统计相邻回调间隔。
- **预期结果**：起流期间回调按 `powerRefreshInterval` 周期持续到达；观察窗口内任意相邻回调间隔 ≤ 5×`powerRefreshInterval`（5 倍为线程调度/系统抖动容错上限），直到窗口结束仍无静默。
- **有效性说明**：覆盖"起流后电量回调停止"的失效模式；判定基于"事件是否持续到达"，不受 ±2% 滞回导致电量值长时间不变的影响。
- **可自动化**：auto（起流后无需人工动作）
- **人工介入**：无。
- **测试结果**：待测试

## 日志/调试（LOG-*）

### LOG-FUNC-001 DEBUG_ENABLED 开关 controller log
- **优先级**：P1
- **测试目的**：验证调试日志开关。
- **流程与逻辑**：`controller.setParam("LOG_PATH", dir)` → `setParam("DEBUG_ENABLED","True")` → 执行 scan/connect → 记录 `dir` 下日志文件大小 → `setParam("DEBUG_ENABLED","False")` → 等待 2s（刹车）→ 记录基线 → 再观察 5s 的增量。
- **预期结果**：True 后生成/增长 `.log` 文件；False 且刹车期结束后，观察期增量为 0（不再写）；关闭后再次开启可恢复写日志。
- **有效性说明**：Android 用 `DEBUG_ENABLED` 参数替代 Python `setDebugEnabled()`；**必须"刹车 + 观察"分离**，避免把缓冲区落盘尾流误判为仍在写。
- **可自动化**：auto
- **人工介入**：无。
- **测试结果**：待测试

### LOG-FUNC-002 LOG_PATH 目录/已存在文件
- **优先级**：P1
- **测试目的**：验证日志路径。
- **流程与逻辑**：`setParam("LOG_PATH", newDir)`（不存在目录）；再 `setParam("LOG_PATH", existingFilePath)`（指向已存在文件而非目录），并读取该文件内容。
- **预期结果**：合法目录被接受（返回非 `Error` 开头，目录创建成功并可写入）；指向已存在文件时返回 `"OK"`，按**追加**语义把日志写入该文件——原内容作为前缀保留、不被截断或清空，不崩溃（**追加是期望的逻辑**）。
- **有效性说明**：路径校验以「目录自动创建 + 文件路径追加不丢原内容」为准；Android 目录须为应用可写路径（如 `context.cacheDir/...`），不可写路径应明确报错。
- **可自动化**：auto
- **人工介入**：无。
- **测试结果**：待测试

### LOG-FUNC-003 DEBUG_LOG_PATH=True 生成 profile log
- **优先级**：P1
- **测试目的**：验证设备级日志。
- **流程与逻辑**：`p.setParam("DEBUG_LOG_PATH","True")` → `p.getParam("DEBUG_LOG_PATH")` 读路径/状态 → connect + init + 起流 5s → 检查生成 profile 日志文件。
- **预期结果**：`setParam` 返回 `"OK"`；`getParam` 返回路径或启用状态；对应日志文件生成且非空。
- **有效性说明**：每设备日志；Android 该参数在 profile 上（`controller` 的 `LOG_PATH` 管 controller 级日志），二者需区分。
- **可自动化**：auto
- **人工介入**：无。
- **测试结果**：待测试

### LOG-FUNC-004 日志完整记录 scan/connect 事件
- **优先级**：P1
- **测试目的**：验证日志记录关键事件。
- **流程与逻辑**：先 `setParam("LOG_PATH", dir)` + `setParam("DEBUG_ENABLED","True")`，**再**执行 scan → requireSensor → connect → init → 起流 → disconnect，最后检索日志中的 scan/connect/init 事件关键字。
- **预期结果**：日志中包含 scan/connect（及 init/起流）阶段事件；早期 scan/connect 日志不缺失。
- **有效性说明**：顺序必须是"先开日志再操作"，否则早期日志不落盘；Android 无 `setLogPath(True, dir)` 的布尔首参，等价为 `setParam("LOG_PATH", dir)`。
- **可自动化**：auto
- **人工介入**：无。
- **测试结果**：待测试

### LOG-FUNC-005 log(msg, level) 写入应用日志
- **优先级**：P1
- **测试目的**：验证应用日志接口。
- **流程与逻辑**：开启日志后，`controller.log("APP-CTRL-D","D")`、`controller.log(...,"I"/"W"/"E")`，以及 `p.log("APP-PROFILE-W","W")`；检索日志文件中的应用消息。
- **预期结果**：各 level 消息均写入，带应用标记（`[App]`）；profile 未启用日志时 `p.log` 回退到 controller 日志，不丢失、不崩溃。
- **有效性说明**：应用日志正确；level 仅支持 D/I/W/E，非法 level 需记录实际行为（忽略/降级），不得崩溃。
- **可自动化**：auto
- **人工介入**：无。
- **测试结果**：待测试

### BATT-FUNC-005 getCachedPower 返回缓存电量且不发起新请求
- **优先级**：P1
- **测试目的**：验证缓存电量读取快速、可用，且不会因频繁调用触发额外 BLE 请求。
- **流程与逻辑**：连接后先读取一次真实电量建立缓存 → 连续调用 `getCachedPower()` 多次，记录返回与耗时；对比 `getBatteryLevel()`。
- **预期结果**：缓存值与最近一次真实电量一致（允许刷新周期内差异）；调用不阻塞；不崩溃。
- **有效性说明**：UI 高频刷新电量应走缓存接口，避免 BLE 拥塞。
- **可自动化**：auto
- **人工介入**：无
- **测试结果**：已实现（Demo 自动化，待真机验证）
