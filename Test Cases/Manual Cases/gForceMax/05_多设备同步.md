# gForceMax 多设备同步用例（MULTI-*）

> 本组需 **≥2 台 gForceMax**（或 ≥2 台已登记在 `config.json` 的设备）。若只有 1 台，整体"跳过（缺设备）"，不判失败。
> **Android 口径**：`controller.multiStartDataNotification(profiles, timeoutMs, maxDelayDispersionMs, maxAttempts)`
> 与 `controller.multiStopDataNotification(profiles, timeoutMs)` 为**异步回调式**接口，通过
> `{ results: Map<mac, Boolean>, errors: Map<mac, String> }` 返回逐台结果（需用 `suspendCancellableCoroutine`
> 包装等待）；Python 的同步返回 `list[{'mac','ok','error'}]` 不适用。
> `getStartTimeStamp()`/`getDelay()` 返回 `Int`（32 位毫秒），跨设备散布需按 `(x & 0xFFFFFFFF)` 归一化后求差。

### MULTI-FUNC-001 两台同时起流
- **优先级**：P1
- **测试目的**：验证多设备同步起流。
- **流程与逻辑**：扫描并连接 init 两台 → 调 `multiStartDataNotification(profiles, 30000, 5, 3)` 并等待回调 → 检查 `results` 逐台为 `true`、`errors` 为空 → 确认两台 `isDataTransfering()==true`。
- **预期结果**：两台均起流成功；回调 `results` 覆盖两台 MAC。
- **有效性说明**：同步起流核心能力；Android 回调式接口需等待 `errors/results` 返回，不能只看调用是否抛异常。
- **可自动化**：auto
- **人工介入**：无（需 ≥2 台设备）。
- **测试结果**：待测试

### MULTI-FUNC-002 两台同时停流
- **优先级**：P1
- **测试目的**：验证同步停流。
- **流程与逻辑**：`multiStopDataNotification(profiles, 10000)` 等待回调 → 检查逐台 `results` 为 `true`、两台 `isDataTransfering()==false`。
- **预期结果**：两台均停流，回调无错误。
- **有效性说明**：同步停流；停流后数据回调应停止（允许缓冲尾包）。
- **可自动化**：auto
- **人工介入**：无（需 ≥2 台设备）。
- **测试结果**：待测试

### MULTI-FUNC-003 某台未 Ready 不影响其余起流
- **优先级**：P1
- **测试目的**：验证部分失败不影响整体。
- **流程与逻辑**：一台完成 Ready + init，另一台仅 `requireSensor` 不 init（或保持未连接）→ `multiStartDataNotification` → 检查逐台结果。
- **预期结果**：Ready 台 `results=true` 并正常起流；未 Ready 台 `results=false` 且 `errors` 含该 MAC 的原因；其余设备不受影响。
- **有效性说明**：容错能力；不得整批回滚导致 Ready 台也被停流。
- **可自动化**：auto
- **人工介入**：无（需 ≥2 台设备）。
- **测试结果**：待测试

### MULTI-FUNC-004 首包时差 ≤ maxDelayDispersionMs
- **优先级**：P1
- **测试目的**：验证同步对齐质量。
- **流程与逻辑**：用默认参数（`maxDelayDispersionMs=5`、`maxAttempts=3`）`multiStart`，收集两台首包 `getStartTimeStamp()`，按 32 位归一化求差；超差时 SDK 应自动停流重试至 `maxAttempts`。
- **预期结果**：时差 ≤ 5ms；重试后仍超差则回调 `errors` 明确失败原因。
- **有效性说明**：同步精度指标；BLE 环境抖动可能使实测略超差，需连续 3 轮统计，超差且重试无效才判 FAIL。
- **可自动化**：auto
- **人工介入**：无。
- **测试结果**：待测试

- **有效性说明**：参数语义正确；`-1` 不得被误判为非法参数。
- **可自动化**：auto

### MULTI-FUNC-006 混合型号放宽参数

- **有效性说明**：跨型号兼容；`config.json` 未登记第二型号或缺设备时 SKIP，不判失败。

### MULTI-FUNC-007 已起流设备再次 multiStart（restart 语义）
- **优先级**：P1
- **测试目的**：验证重启语义。
- **流程与逻辑**：先让一台单独起流，再对两台调 `multiStartDataNotification`，确认已起流设备先停后与空闲设备同刻起流。
- **预期结果**：`results` 全 `true`，无异常；已起流设备状态不残留双份流（数据回调不重复）。
- **有效性说明**：状态迁移正确；观察首包时间戳应体现"同刻"而非沿用旧会话。
- **可自动化**：auto
- **人工介入**：无（需 ≥2 台设备）。
- **测试结果**：待测试

### MULTI-FUNC-008 两后端各测对齐下发
- **优先级**：P1
- **测试目的**：验证后端同步路径（**保留源 ID，Android 不适用**）。
- **流程与逻辑**：Android 只有系统原生 BLE 后端（`controller.registerBleBridge(context)`），无 bumble/bleak 切换，不执行"双后端"对照。若要覆盖同步路径差异，可重复 MULTI-FUNC-001 三次取统计。
- **预期结果**：不适用。Android 无 dongle/后端切换。
- **有效性说明**：本用例在 Android 侧标 `@Ignore("Android 固定系统原生 BLE，无后端切换")`；同步链路已由 MULTI-FUNC-001/004 覆盖。
- **可自动化**：manual
- **人工介入**：无（不执行）。
- **测试结果**：待测试

### MULTI-FUNC-009 跨设备 startTimeStamp 散布与 getDelay 符合预期
- **优先级**：P1
- **测试目的**：验证时延指标。
- **流程与逻辑**：同步起流后统计两台首批 `getStartTimeStamp()` 的散布、各自 `getDelay()`；重复 3 轮记录均值/最大值。
- **预期结果**：散布在 `maxDelayDispersionMs` 量级内；`getDelay()` 为有限正值（ms），无负数/异常大值。
- **有效性说明**：同步与延迟量化；`getDelay()` 是起流时序锚点，不是信号数据，不能用它判断数据质量。
- **可自动化**：auto
- **人工介入**：无（需 ≥2 台设备）。
- **测试结果**：待测试

### MULTI-BND-001 multiStart/multiStop 空集合 / 单台 / 非法参数不崩溃
- **优先级**：P1
- **测试目的**：验证多设备起停接口对空集合、单台设备、非法参数都能安全处理。
- **流程与逻辑**：`multiStart(emptyList())`、`multiStart(单台)`、`multiStart(含 null/非法对象)`；`multiStop` 同理。
- **预期结果**：空集合返回 `false`/空结果且不崩溃；单台正常起流；非法参数被拒绝。
- **有效性说明**：多设备接口必须容错，不能因空集合或单台场景崩溃。
- **可自动化**：auto
- **人工介入**：无
- **测试结果**：已实现（Demo 自动化，待真机验证）

### MULTI-BND-003 multiReplayBinFile paths/sensors 长度不匹配或空串被拒绝
- **优先级**：P1
- **测试目的**：验证多 bin 回放接口对参数不一致、空路径、空 sensors 的容错。
- **流程与逻辑**：构造 `paths` 与 `sensors` 长度不一致、含空串路径、`sensors=null` 三组参数调用 `multiReplayBinFile`。
- **预期结果**：返回错误或被拒绝；不崩溃；不产生半启动回放。
- **有效性说明**：多 bin 回放参数由上层拼装，长度不匹配是常见错误。
- **可自动化**：auto
- **人工介入**：无
- **测试结果**：已实现（Demo 自动化，待真机验证）

### MULTI-ROB-001 multiStop 重复调用幂等

- **有效性说明**：页面退出与异常兜底可能重复调用停流。
