# gForceMax 控制器与扫描用例（CTRL-*）

> **Android 口径**：`SensorController` 通过 `SensorController.getInstance()` 获取，初始化时调用
> `controller.registerBleBridge(context)` 绑定系统原生 BLE；扫描为挂起函数 `controller.scan(timeoutMs)`，
> 返回 `List<BleDevice>`（**无** `startScan`/`stopScan`/`isScanning`/周期扫描回调，也**无**后端切换/dongle）。
>
> **2026-11 补充**：1.4.6 AAR 已提供 `startScan/stopScan/isScanning` 与 `setOnScanStateChangeListener`；
> 上文“无 startScan”为旧版接口说明，涉及扫描起停的新增用例以文末「补充用例」为准。
> 目标设备匹配统一走 `TestConfig.matchesTarget()`（MAC 精确 > 广播名后四位 identity），gForceMax 的
> identity 为 `9AA7`、MAC 为 `BC:93:2A:3F:9A:A7`（登记在 `Test Cases/Automation/config/config.json`）。

### CTRL-FUNC-001 蓝牙未开启时 isEnable()==false，scan 被拒绝
- **优先级**：P0
- **测试目的**：验证控制器感知系统蓝牙状态并在关闭时拒绝扫描。
- **流程与逻辑**：人工关闭 Android 蓝牙 → 读 `controller.isEnable()` → 挂起调用 `controller.scan(3000)`，观察返回值/异常/耗时。
- **预期结果**：`isEnable()==false`；`scan()` 返回空列表或抛出受控异常（不崩溃、不阻塞超过超时时间）。
- **有效性说明**：若蓝牙关闭仍能"成功扫描"并返回设备列表，说明 SDK 未校验硬件使能，属缺陷。
- **可自动化**：semi-auto
- **人工介入**：人工在系统设置中关闭/开启蓝牙。
- **测试结果**：待测试

### CTRL-FUNC-003 单次 scan 成功返回设备列表且不残留扫描态
- **优先级**：P0
- **测试目的**：验证 Android 单次扫描的返回与结束语义。
- **流程与逻辑**：`controller.scan(3000)` → 记录返回 `List<BleDevice>` → 立即再调一次 `scan(3000)` → 记录两次耗时与结果；扫描返回后观察 `setOnScanResultListener` 是否仍有回调。
- **预期结果**：首次调用在约 3s（±1s）内返回非空列表；第二次调用同样正常返回；扫描返回后不再有扫描结果回调。
- **有效性说明**：Android **无** `startScan`/`stopScan`/`isScanning`，状态翻转断言改为"扫描调用返回即结束、无残留回调"；若返回后仍持续回调，说明扫描未正确停止。
- **可自动化**：auto
- **人工介入**：无（需设备开机在扫描范围内）。
- **测试结果**：待测试

### CTRL-FUNC-005 setOnScanResultListener 扫描期间回调
- **优先级**：P1
- **测试目的**：验证扫描结果回调（替代 Python 的 `onDeviceFoundCallback`）。
- **流程与逻辑**：注册 `controller.setOnScanResultListener { devices -> ... }` → `controller.scan(3000)` → 统计回调次数、每次回调中的设备数与是否含 gForceMax。
- **预期结果**：扫描期间至少收到 1 次回调，回调列表含 gForceMax；同一设备不因重复回调造成重复计数错误。
- **有效性说明**：Android 只有 `setOnScanResultListener`（无 `onDeviceFoundCallback`）；回调节律由系统 BLE 扫描决定，不强制 3s 周期。
- **可自动化**：auto
- **人工介入**：无。
- **测试结果**：待测试

### CTRL-FUNC-007 requireSensor(mac) 有效/无效
- **优先级**：P0
- **测试目的**：验证由扫描结果创建 `SensorProfile`。
- **流程与逻辑**：对扫描命中的 gForceMax 调 `controller.requireSensor(device.mac)`；再对不存在 MAC `00:00:00:00:00:00` 与非 MAC 字符串 `"not-a-mac"` 调用。
- **预期结果**：有效 MAC 返回非空 `SensorProfile`；无效 MAC 返回 `null`，不崩溃。
- **有效性说明**：Kotlin 参数为**非空 String**（无 Python 的 `None`），"无效"用空串/非法 MAC 表达；返回 `null` 即表示创建失败。
- **可自动化**：auto
- **人工介入**：无。
- **测试结果**：待测试

### CTRL-BND-001 scan(timeoutMs) 6 点边界
- **优先级**：P1
- **测试目的**：验证扫描超时参数边界。
- **边界定义（依据）**：`scan(timeoutMs: Long)`，以 `Long.MAX_VALUE`（9223372036854775807）为上限参考；实际执行用可控上限 `MAX_EXEC = 2147483647`（int32 上限）避免长时间阻塞，并记录该替换原因。
- **流程与逻辑**：分别传 `0、1、MAX_EXEC-1、MAX_EXEC、-1、MAX_EXEC+1`，每次记录返回列表大小、耗时、是否抛异常。`0/1` 与超大值需配合 `@Test(timeout=...)` 保护，避免挂起。
- **预期结果**：所有入参均不得导致进程崩溃；`0`/`1` 应立即返回（允许空列表）；负值应被拒绝（抛 `IllegalArgumentException` 或返回空列表）；超大值应在 JUnit 超时保护内结束。
- **有效性说明**：Android 无 Python 的 `ValueError` 显式校验约定，判据放宽为"不崩溃 + 不永久阻塞"；若任一边界值导致 instrumentation 进程崩溃判 FAIL。
- **可自动化**：auto
- **人工介入**：无。
- **测试结果**：待测试

### CTRL-ROB-001 扫描期间重复 scan 调用
- **优先级**：P1
- **测试目的**：验证扫描并发健壮性。
- **流程与逻辑**：在协程中连续发起 3~5 次 `scan(3000)`（可 `async` 并发），观察是否死锁/异常；结束后再执行一次 `scan(3000)` 确认控制器仍可用。
- **预期结果**：无死锁、无未捕获异常；调用串行化或返回明确错误；后续扫描仍能正常返回。
- **有效性说明**：Android 无 `startScan`/`stopScan` 交替语义，重复调用改为并发 `scan` 压力；线程/协程安全是本用例重点。
- **可自动化**：auto
- **人工介入**：无。
- **测试结果**：待测试

- **有效性说明**：空/非法 MAC 不应创建 profile；使用从未创建的合法 MAC，避免误命中其它用例登记的设备。
- **可自动化**：auto
- **人工介入**：无
